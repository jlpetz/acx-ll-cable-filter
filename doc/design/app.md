# App spec (nf-app → `noise-filter.exe`, v0)

## Start-up (main.rs)
- **The CPU gate, first:** the build is x86-64-v3 (`.cargo/config.toml`). `main` calls
  `cpu_check::gate` before anything else (the panic hook, the log, the console, the single-instance
  check, the memory pool), and the rest runs in `app_main`, which is never inlined into it. A CPU
  that lacks a v3 feature (CPUID and XCR0, read directly) gets an ASCII `MessageBoxA` naming what's
  missing, the same text on standard error if there is one, and exit code 5. The launcher does the
  same on standard error only, and in a console of its own waits for Enter before it exits.
  `cpu_check.rs` says why the way there avoids AVX and BMI instructions;
  `tools/check_cpu_gate_asm.py` checks that in the release asm (`doc/dev/build-report.md` §11).
- **Allocator:** `#[global_allocator] static GLOBAL: nf_mem::RtAllocator = nf_mem::RtAllocator::new();`
- **Memory, in this order, before any engine thread exists:**
  1. `nf_mem::privilege::enable_lock_memory_privilege()`; a missing privilege isn't an error;
  2. `nf_mem::install_pool(PagePolicy::Large, 32 MiB)`;
  3. `nf_mem::set_working_set_minimum(64 MiB)`; 128 MiB in an `onnx` build, whose ONNX Runtime code and heap are about
     20-40 MB more (TODO 5, 6).
  Log the `PoolStatus`. The engine reads `nf_mem::pool_status()` for its status line.
- **Logging:** a small `log::Log` that appends to `%LOCALAPPDATA%\noise-filter\noise-filter.log`
  (with a 1 MB rotation to `.old`). Only non-real-time threads log. Add a panic hook that logs the
  panic and its location. Release is `panic = "abort"`.
- **Window or console:** a double-click opens only the window, never a console. CLI subcommands
  from a terminal print to it. Choose the mechanism from `doc/dev/api/windows-reactor.md`:
  - TMR's console subsystem plus the `consoleAllocationPolicy` manifest, which works on 26100+;
  - or the windows subsystem plus `AttachConsole(ATTACH_PARENT_PROCESS)` for subcommands.

  Windows 11 22000-26099 must not flash a console on a double-click. Document the choice in
  `main.rs`. The choice made: the windows subsystem plus `AttachConsole(ATTACH_PARENT_PROCESS)`.
- **The console launcher:** cmd.exe and PowerShell don't wait for a windows-subsystem exe, so
  `noise-filter-cli.exe` (console subsystem, about 140 KB) sits next to it. It ignores Ctrl+C
  itself, runs `noise-filter.exe` with the same arguments and inheritable copies of its standard
  handles, waits, and exits with the child's code; the child attaches to the console and handles
  Ctrl+C. Copied to `noise-filter.com`, a plain `noise-filter ...` in a terminal runs it (PATHEXT
  puts .COM first). Nothing creates the `.com` yet, and Win+R or Start search would then pick it
  too and flash a console: the packaging decides (TODO #18). Without the launcher, `run` warns
  once that Ctrl+C may not reach it.
- **One window:** a second window launch finds the first (a named mutex, then its visible window)
  and brings it forward instead of opening another. The headless `run` isn't guarded: both can
  feed the cable.

With both exclusive by default, a `run`, `latency` or `quality` on the window's mic or cable can't start while the window's filter runs (the device is held in exclusive mode: the start error says another copy of the filter may hold it, and `run` retries): stop the window's filter first. The adaptive target walks down after four minutes (a window, and a second to confirm it) to what the delivery needs (an underrun under the fixed target puts it back and holds it there for 10 minutes, then 20, and the third keeps it fixed: up to three glitches a run that the fixed target wouldn't have). `--help` says what each costs and when to turn it off. The start line names each stream's asked-for mode and the target's (`exclusive output, exclusive mic, adaptive output target`), the stream lines the format of an exclusive stream (`exclusive 16-bit`). Ctrl+C stops it cleanly (`SetConsoleCtrlHandler`). Device IDs accept a name substring too (first match, case-insensitive). |

## The noise model (TODO 5)
- `--model NAME` (`run`, `latency`, `quality`, `process`; `bench` too) sets `ProcessingConfig.noise_model`: `rnnoise` (the
  default) or a model pack's id. The parser checks only its syntax (the pack id rule, `[a-z0-9][a-z0-9-]{0,63}`); the start
  resolves it (`nf_engine::models`), and says what's wrong: "needs a build with --features onnx", or "isn't installed: python
  -I tools/fetch_models.py ID". There is no fallback to RNNoise. `--high-band model|zero|pass` sets
  `ProcessingConfig.high_band` (live). `--model-depth auto|N` (1-4; default auto, `ProcessingConfig.model_depth` 0) sets how
  many blocks behind its worker a pack's model runs: each adds 10 ms, and a wake that brings more blocks back to back than
  it plays the unfiltered mic for each one over. Auto picks it at each start: 1 when the mic delivers a block a wake (as
  an earlier run in the process measured it, opened the same way; unmeasured, the exclusive mic at a period of a block or
  less), else 2; offline (`process`), 2 (engine.md, "The inference worker"). The start's Engine line says which and why
  ("model depth 1 (auto: the mic delivers a block at a time)"), and `quality --save` writes the depth the start chose into
  `chain_config.json`. A `--config` file carries all three (`processing.noise_model`, `processing.high_band`,
  `processing.model_depth`); the window's settings file is read as the window reads it, so one saved before the automatic
  depth (no `"version"`, `model_depth` 2: the default then, which the window never sets) is automatic, and a bare engine
  config (`chain_config.json`) keeps its depth.
- With a pack, `run`'s status line adds `model misses N run P µs bursts B` (the worker's misses, its run time's p99, and the
  wakes that brought more than one block), and a soak's summary (`run --seconds`) a `wakes` line for every model: the wakes
  that processed 1, 2, 3 and 4 or more blocks, what a pack's worker would miss there at depths 1, 2 and 3, and, with a pack,
  what it did miss.
- **The `onnx` feature** (nf-app → nf-engine → nf-ort), off by default: the default exe is unchanged. The owner builds the
  evaluation variant with `cargo build --release --features onnx` (the first build downloads ONNX Runtime, about 32 MB,
  checked by ort-sys). In it ONNX Runtime's C++ static initialisers run before `main`, so before the CPU gate, and need AVX2;
  `check_cpu_gate_asm.py` passes its Rust asm but can't see into the library. It needs the C++ runtime (`MSVCP140.dll`)
  installed. DirectML, D3D12 and DXGI are delay-loaded and never loaded.
- UL-UNAS is for evaluation only (its patent question is open, TODO 5): 50 ms of stream latency against RNNoise's 10 at
  depth 2 (40 at depth 1, which the automatic depth picks with the exclusive mic), about 6% of a core on its worker, and the pack is fetched by the developer, never bundled.

## The flight recorder (`run --flight`, `devices --check`; TODO 13, 21)
The engine's flight recorder (`Engine::arm_flight_recorder`; engine.md, "The flight recorder") keeps the last 10 s of every
block's facts and, when the output, the mic, the audio thread, the echo reference or the model misbehaves (an underrun, a
deficit or a coarse drop; a stall, a glitch, a skip or an overflow; a late wake or a slow block; a jump, a burst of short takes
or the reference lost; a miss; a fault that stops the audio), waits 3 s more and writes the window into a folder of its own:
`flight_blocks.csv` (a row a block), `summary.txt` (what triggered, when by the local clock and since the start, the window,
and a reading of the facts around it in words: a held-up thread, a mic that stopped delivering, an output that ran dry), and
with `--flight-audio` the last 5 s of the chain's mic, reference and output as WAVs. Triggers that come together (within half
a second, or in a dump's post-roll and of a kind it holds) share a dump, the most serious leading it; another kind's gets its
own, even inside the first one's window. At most one dump a minute and 3 in all for each kind of trigger, 20 in all (so one
that keeps misbehaving can't crowd out another later); the rest are counted, by kind.
- **`run --flight [DIR]`** arms it before the start (`DIR`: the next argument when it isn't an option, or `--flight=DIR`;
  `--flight-audio` arms it too), so it holds the first run from its first block and follows the engine's own restarts. It says
  so once, notes each dump as it's written (`flight: at 110.0 s (2026-11-02 14:03:12.345), an output underrun (with
  output-deficit, late-wake): <folder> <reading>`), and the summary ends with its `flight` line: the dumps, the triggers the
  limits held back by kind, blocks lost, write errors, or `nothing triggered in N blocks`. A recorder that can't be armed
  (its folder can't be made) stops `run`, which was asked for it. It's stopped after the engine, so a trigger in its post-roll is dumped
  with what there is. Off without `--flight` (ours: `run` is the owner's soak tool; the window's always-on use is TODO 15's
  and 21's to decide).
- **`devices --check`** arms it always (`--flight DIR` and `--flight-audio` as `run`'s), and its report ends with "Flight
  recorder:" naming each dump (its folder, what triggered it and its reading), or saying nothing it watches for went wrong.
  One that can't be armed is a warning there, and the check runs without it (the report says so): the check is the
  diagnostic, and wasn't asked for the recorder.
- **Where (decided, ours):** `%LOCALAPPDATA%\noise-filter\flight` by default (`logger::flight_dir`), beside the log: the app's
  own folder, which a user sends with a report. A dump is about 0.4 MB with the facts alone and 5 MB with 5 s of audio, and
  after each dump only the newest 20 are kept there (the engine's `keep_dumps`; older dump folders are deleted, only those
  named exactly as the recorder names them, `flight-YYYYMMDD-HHMMSS-<trigger>[-N]` with a `summary.txt`; nothing else in the
  folder is touched), so it stays under about 10 MB (100 MB with audio). A `DIR` given gets the same retention.
- **The GUI** can use the same API later: `Engine::arm_flight_recorder(FlightConfig::new(dir))`, and `FlightRecorder::stats`
  for the dumps so far (each with its folder, trigger, time and reading).

## Exit codes
0 is OK; 1 is a usage error; 2 is an engine, device or file error; 3 is a test with no valid result
(`latency`: no valid repetition; `quality`: the recording didn't line up with the scene; either one
cancelled; `run --seconds` cut short by Ctrl+C with no glitch; `devices --check` cancelled in its first 3 s);
4 is the large-page helper started without elevation. `nf_mem::privilege::HELPER_NOT_ELEVATED`
holds the 4 the window reads, and a compile-time check ties it to `Exit::NotElevated`. 5 is a CPU
without x86-64-v3's features (`Exit::UnsupportedCpu`, tied by a compile-time check to
`cpu_check::EXIT_CODE`, which the CPU gate returns in both exes). 6 is `run --seconds` (a soak) that
wasn't clean (`Exit::Glitched`): mic glitches or stalls, output underruns or coarse drops, a fault that
stopped it (a second not running, a restart), or a real-time heap allocation, so a soak reads as one code;
it takes precedence over 3. The summary before it says what. A `run` without `--seconds` exits 0 (ours,
not the owner's: an interactive run stopped with Ctrl+C isn't a test, and the adaptive target allows up
to three underruns a run by design).
