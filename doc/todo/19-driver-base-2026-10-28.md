## 1. The base

**Primary: the ACX AudioCodec sample** (WDS `Acx/Samples`), cut down, plus MIT pieces from microsoft/low-latency-audio (LLA). **Fallback: SimpleAudioSample** (WDS `simpleaudiosample`, PortCls WaveRT), with a rewritten clock.

Both are better bases than LLA itself. LLA is 48.5k lines on yamaha-main, 13.7k of them USB descriptor parsing alone. Its PrepareHardware has no path that works without a USB device (LLA `src/uac2-driver/Device.cpp#L433-667`).

**You're right that both are samples, not drivers you can ship.**
- **AudioCodec**
  - Root-enumerated, `ROOT\AudioCodec` (`Acx/Samples/AudioCodec/Driver/AudioCodec.inf#L32-36`), with one render and one capture endpoint (`Driver/Device.cpp#L181-183`, `#L251-255`).
  - Already runs ACX's event-driven two-packet mode (INF `#L76-78`, `#L88-90`). Each stream has its own high-resolution timer, rescheduled at absolute QPC times (`Common/StreamEngine.cpp#L244-253`, `#L561-637`).
  - But: capture is a sine or a WAV file (`#L926-938`), render goes to WAV files (`#L867`), formats are 16-bit PCM only, and it declares no packet sizes, so periods default to 10 ms (Learn `audio/acx-streaming`).
  - About 11.2k source lines, of which 3,341 are tone, WAV and keyword scaffolding.
- **SimpleAudioSample**
  - Root-enumerated (`simpleaudiosample/Source/Main/SimpleAudioSample.inx#L29`), with a speaker and a mic (`Source/Filters/minipairs.h#L75-170`).
  - Capture is a sine; render audio is thrown away by default (`Source/Main/adapter.cpp#L49-51`).
  - It ticks a 1 ms timer and works out notifications and positions in whole milliseconds (`Source/Main/minwavertstream.cpp#L526-529`, `#L1255-1267`, `#L1315-1328`). So a 128-frame (2.67 ms) period gets notified every 2 ms.
  - About 15.4k lines.

Neither sample passes render audio to capture, and neither accepts audio from an app. What they do provide is the tedious part: device and endpoint registration, WaveRT buffers, position reporting and event notification. The audio source and sink we have to replace are code we would write on any base (my judgment).

**Why AudioCodec first**
- Its clock is already the right design. SimpleAudioSample's would have to be rewritten.
- LLA's stream engine is a cut-down copy of this sample under MIT, down to the sample's timer variables left commented out (LLA `src/uac2-driver/StreamEngine.cpp#L160`, `#L273-275`).
- MinMidi2 is a second root-enumerated Microsoft ACX driver under MIT (`MinMidi2.inf` L59-63).
- Someone has already built an app-fed ACX microphone in about 1k lines, and it runs Verifier-clean in a VM (https://github.com/NezucloudResearch/acxmic/tree/22db6c4, README "Status").
- The only other ACX sample, SdcaVad, is 33k lines and specific to SoundWire.

**Fall back to SimpleAudioSample if** ACX blocks us, for example on float formats (§3). Every open-source cable driver we found uses PortCls, and SYSVAD shows the PortCls version of the packet-size code (WDS `sysvad/TabletAudioSample/minipairs.h#L71-135`).

**Existing open-source drivers don't fit**
- **Virtual-Audio-Driver**
  - Its mic writes zeros (https://github.com/VirtualDrivers/Virtual-Audio-Driver/blob/bb34fba/Source/Main/minwavertstream.cpp#L1392-L1422).
  - The shipped binary is signed by SignPath Foundation, not Microsoft (https://github.com/VirtualDrivers/Virtual-Driver-Installer).
  - Correction to the 2026-10-26 notes: it is derived from SimpleAudioSample, not SYSVAD (unchecked).
- **Unitra.Mic.Driver** is Microsoft attestation-signed and has a working render-to-capture ring. But it is 16-bit, has no app feed, and uses separate clocks for the two sides (https://github.com/unitra-ai/Unitra.Mic.Driver/blob/68c71a4/Source/Main/minwavertstream.cpp#L1434-L1515). It is useful as a second benchmark.
- **audiorouter's driver** (MS-PL) is the closest design: an app-fed shared section and 128-frame packet sizes (`drivers/audiorouter-virtual/Source/Filters/minipairs.h` L45-55). But:
  - it is about 18k lines;
  - its own plan says VM continuity and latency "do not meet qualification" (`docs/plans/active/virtual-cable.md` L3-6);
  - the rest of the repo is GPL-3.0 (https://github.com/MrDesjardins/audiorouter/tree/358e03e).

### Changes needed on the AudioCodec base
1. **Strip** ToneGenerator, WaveReader, SaveData and KeywordDetector, plus their setup code (`Device.cpp#L236-240`, `#L302-303`).
2. **Formats.** 48 kHz only. Add float32 and 24-in-32, mono and stereo (`Common/CaptureCircuit.cpp#L325-372`, `Common/RenderCircuit.cpp#L295-342`, `Inc/AudioFormats.h`).
3. **Small buffers.**
   - Publish `DEVPKEY_KsAudio_PacketSize_Constraints2` on the KSCATEGORY_AUDIO interface before the interface is enabled (Learn `ddi/ksmedia/ns-ksmedia-_ksaudio_packetsize_constraints2`).
   - Do it right after `AcxDeviceAddCircuit` (`Device.cpp#L251-255`). That placement is an inference.
   - Start with a 1 ms minimum and 96-128-frame sizes for RAW and DEFAULT modes. A mode value that isn't above the minimum is ignored. Only apps on the same endpoint *and* the same mode switch to the small buffer (Learn `audio/low-latency-audio`).
4. **Engine bugs** (inference, unchecked).
   - `UpdatePosition` subtracts a value in 100 ns units from a byte position (`StreamEngine.cpp#L625`, `#L654`).
   - When the timer fires late, the code calls itself recursively at DISPATCH_LEVEL (`#L619-630`).
5. **App feed** (new `Control.cpp`, `nf_ioctl.h`, `Ring.h`).
   - A KMDF control device object (Learn `wdf/using-control-device-objects`) receives a pending `METHOD_OUT_DIRECT` IOCTL that hands over a ring buffer the app allocated.
   - Windows locks the pages and gives the driver an MDL (Learn `kernel/buffer-descriptions-for-i-o-control-codes`).
   - Map it with `MdlMappingNoExecute` and treat the ring header as untrusted. On cancel, unpublish the ring under a lock before completing the request.
   - Capture `ProcessPacket` (`StreamEngine.cpp#L986-1011`) copies from the ring and fills with zeros on underrun.
   - Calling this the safest design is my judgment. MinMidi2 does the opposite: it maps a driver-owned buffer into the app (`StreamEngine.cpp` L580-650).
6. **Clock drift.** The real mic and our QPC-paced endpoint will drift apart, so the app has to steer by how full the ring is (inference). ntpods reports the same drift (https://github.com/arctumn/ntpods/tree/main/windows/drivers/mic). It is GPL, so read it only; don't copy code.
7. **Loopback pairs.**
   - Render `ProcessPacket` (`#L851-868`) writes into a per-pair ring that the capture side reads after a fixed pre-roll.
   - Both sides compute position from QPC at the nominal rate (`#L651-654`), so a pair shares one clock (inference).
   - Build the circuits from a table (`Device.cpp`, `Driver/DriverSettings.h`, the INF).
8. **Names.** Use `EvtAcxPinRetrieveName` and the INF strings. Remove the toggle that switches the mic's name back and forth (`CaptureCircuit.cpp#L554-562`).
9. **INF.** `ROOT\NoiseFilterAudio`, `10.0...22621`, with `[DeviceInstall32] AddDevice` as in `MinMidi2.inf` L59-63. I infer, but haven't confirmed, that pnputil alone could then install it.
10. **Rust client** crate.

**Effort (estimate).** About 3,500-4,500 lines when done. 19-34 working days for one developer who knows KMDF, including 4-6 days for the control device and ring, 2-4 for loopback pairs, and 4-8 for benchmarking against VB-CABLE.

### What to borrow from LLA (MIT, yamaha-main branch only)
- The packet-size struct and `AddPropertyToCircuitInterface` (LLA `src/uac2-driver/CircuitHelper.cpp#L49-81`, `#L944-997`). Note that main still declares 7 ms (LLA-main `src/uac2-driver/CircuitHelper.h#L64-89`).
- StreamEngine's two-packet allocation and state machine (`StreamEngine.cpp#L119-405`), without the calls through to the USB engine.
- The user-buffer handling: user-mode probe and lock, no-execute mapping, a snapshot of the header, user events, and per-file cleanup (`AsioBufferObject.cpp#L83-156`, `#L185-409`; `Device.cpp#L2792-2856`). main still probes with KernelMode (LLA-main `src/uac2-driver/AsioBufferObject.cpp#L124`), so take the yamaha-main version.
- Skip:
  - the USB engine;
  - the 100 µs HIGH_PRIORITY mixing thread (`MixingEngineThread.cpp#L98-170`);
  - `RtPacketObject.cpp`, which has an open fix for a crash race (https://github.com/microsoft/low-latency-audio/pull/33);
  - `USBAsio.dll`, which needs the Steinberg ASIO SDK, now proprietary or GPLv3 (https://www.steinberg.net/asiosdk).

**Licence.**
- WDS is MS-PL. Section 3(D) allows source distribution "only under this license" (https://github.com/microsoft/Windows-driver-samples/blob/bb68ed5e770bce04dc5395ec9258dafab034184d/LICENSE#L22).
- So a driver directory derived from AudioCodec stays MS-PL. The app and the client crate can stay MIT OR Apache-2.0.
- Keep the Microsoft/Yamaha MIT notices on anything taken from LLA or MinMidi2.
- If the driver were built only from those MIT copies, with AudioCodec used as a reference, it might be possible to use one permissive licence throughout (inference, not legal advice).

## 3. Risks, open questions, first spike

- **Small periods.** We don't know whether the audio engine will grant 2-3 ms periods on a virtual ACX endpoint. Microsoft's own ACX driver has an open issue where IAudioClient3 is offered only 10 ms (https://github.com/microsoft/low-latency-audio/issues/22).
- **Timer jitter.** High-resolution timers fire late, never early. The ACX study reads Learn as allowing up to about 1 ms of lateness (Learn `kernel/high-resolution-timers`, unchecked). EC2 vCPUs may be worse than a desktop (inference).
- **Float32 under ACX.** No Microsoft sample shows a float device format (inference). audiorouter's PortCls driver defaults to float32 (`docs/spec/17-virtual-cable.md` L134). Keep 24-in-32 as a fallback.
- **Minimum Windows.** Learn lists ACX 1.1 from Windows 10 2004 (Learn `audio/acx-version-overview`). ntpods reports that its ACX build needs 22H2+. LLA's preview uses 22621 because of KMDF 1.33 (LLA-P `src/installers/low-latency-audio-installer/Branding.wxi#L48-53`). Our 22621 floor should be fine, but confirm it.
- **If we copy LLA's property-based handover:** ACX may run handlers outside the caller's process (Learn `audio/acx-irps`), which is why MinMidi2 attaches to the requesting process (`Stream.cpp` L626-670).
- **Signing.**
  - Learn says "For testing purposes only, you can submit your drivers for attestation signing", and that Server 2016+ loads only dashboard-signed drivers that have passed the HLK (Learn `dashboard/driver-signing-offerings`).
  - That wording dates from 2023, not 2026 (MicrosoftDocs commit 661cf1c67).
  - Unitra ships an attested driver, and LLA's preview plans attestation (LLA-P `src/installers/README.md#L100-120`), so Windows client PCs probably still load attested drivers (inference).
  - The dev box needs test signing. Secure Boot is off there (`UEFISecureBootEnabled=0`), so test signing can be turned on.
  - Testing with Memory Integrity on needs a signed build on a Windows 11 client (inference).
- **Audio service.** The runner-images workaround starts the audio services before installing a driver (issue 6983 above), so check that Audiosrv is running on the dev box (inference).

## Design note: the app-feed buffer (2026-10-28, after the owner's question)
- **Both ring designs are zero-copy between the app and the driver.** In each, the app writes a shared single-producer ring
  and the driver's timer reads it, with no system call per block. What differs is who allocates the memory and who cleans up.
- **Copies on the path,** per block: the chain's output into the ring (one write; the chain could write in place), then the
  driver's ring-to-WaveRT-packet copy in its timer (a few KB, about 100-200 ns, converting to the endpoint's format), then the
  audio engine's own copies to each recording app. Against the chain's ~85 us a block, the driver's copy is about 0.2%.
- **Writing straight into the WaveRT buffer** (no driver copy) is ruled out:
  - the buffer exists only while some app records the mic;
  - it's two short packets;
  - it drains on the driver's QPC timer while our audio comes on the real mic's clock. The ring holds the cushion between the
    two clocks, and the app steers its drift loop on the ring's fill.
- **App-allocated ring (chosen):** the app allocates it (from its locked pool, so its audio thread never faults) and hands it
  over in one pending `METHOD_OUT_DIRECT` IOCTL. The I/O manager locks the pages for the request's life, and the driver maps
  them `MdlMappingNoExecute` into system space, usable from the timer DPC. When the app exits or crashes, the request is
  cancelled, the driver unpublishes the ring under its lock, and the pages unlock. The header is untrusted: snapshot sizes at
  handover and bounds-check every index. low-latency-audio's `AsioBufferObject` uses this pattern.
- **Driver-allocated, mapped into the app (MinMidi2):** the same speed, but the driver must map and unmap the user view in
  the right process (ACX handlers can run outside it, which is why MinMidi2 attaches to the caller), and unmap before that
  process goes away. Mistakes there bugcheck. Loopback pairs (render to capture, no app) use driver-owned rings.
- **Per-block `WriteFile` (acxmic):** ruled out. It means a kernel copy and a system call every period on the audio thread.

## Also from the studies (not in the synthesis above)
- **A second view on the base.** The forks study concluded that no fork saves real work and that our driver should be a small new
  one: n3dypop/cableloom's structure (original MIT code, about 690 driver lines, one adapter timer driving both halves of each
  render/capture pair from one QPC frame clock, a Rust manager; its README says loading is still unverified), audiorouter's shared
  section and packet-size ideas, and AudioCodec or acxmic as plumbing reference. The synthesis chose AudioCodec as the base; the
  first spike decides. A driver built only from MIT originals (cableloom, low-latency-audio, MinMidi2) could stay permissively
  licensed throughout; anything derived from a Microsoft sample keeps those files MS-PL (MS-PL 3(D)).
- **NezucloudResearch/acxmic** (MIT with MS-PL parts from the ACX samples, created 2026-10-08, 0 stars, test-signed only): an
  app-fed ACX microphone in about 1,000 lines, fed by `WriteFile` to a control device into a spin-locked ring, one high-resolution
  timer per packet on an absolute QPC timeline, Verifier-clean in a VM, median 18.8 ms in their test. It declares no packet-size
  constraints (10 ms periods) and has no render or loopback.
- **Driver revocation risk.** Voicemod reported that Microsoft revoked its virtual audio driver on Insider builds above 22557, and
  a conflict with Vanguard; both were later fixed (https://support.voicemod.net/hc/en-us/articles/5008599085586). A third-party
  audio driver can be blocked by Windows or anti-cheat: keep VB-CABLE working as the fallback output.
