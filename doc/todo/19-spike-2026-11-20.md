## Set-up (2026-11-20)
- **Toolchain, on the box already:** Visual Studio Community 2026 18.12 with the WDK extension
  (`WindowsKernelModeDriver10.0` toolset), WDK and SDK 10.0.28000 (WDK 28000.2526). Frameworks on the box:
  Wdf01000.sys 1.35.26100.3323 (KMDF 1.35), Acx01000.sys 10.0.26100.33822 (ACX 1.1; the WDK's headers have 1.0 and 1.1).
  Audiosrv running.
- **KMDF 1.35** (the owner, 2026-11-20: "target the latest KMDF 1.35"): the newest the WDK has and the box runs. It needs
  Windows 11 24H2 or Server 2025 (26100) and up, so the INF's floor is `10.0...26100` and the catalog is made for
  `10_GE_X64,Server2025_X64`. (1.33 would have kept 22H2 and 23H2.)
- **The base:** the ACX AudioCodec sample at Windows-driver-samples d49bb7d (2026-11-05), imported verbatim into
  `driver/src` (a0cccd1; MS-PL), then changed (KMDF 1.35, the INF floor). The unmodified sample builds (64 KB .sys).
- **WDK 28000 under VS 2026:** two post-build checks fail on tooling, not code. The InfVerif task looks for
  `x86\InfVerif.dll` (it's under `build\10.0.28000.0\bin\x64`), and ApiValidator's `aitstatic.exe` exits 193. The build
  turns both off (`SkipPackageVerification`, `ApiValidator_Enable=false`) and runs InfVerif from `Tools\...\x64`: clean.
- **Release favours speed** (895f9c1): both projects' Release|x64 set `FavorSizeOrSpeed` to `Speed`. The CL tlogs and a
  detailed MSBuild log show `/Ox /Ot /Oy-` on all 13 compiles, where the WDK default had given `/Ox /Os`. The .sys
  grew from 54,272 to 57,856 bytes on the same sources. The spike's measurements so far used `/Os` builds.
- **Test signing** (`driver/scripts`, ported from TMR-MD's build.ps1, which worked on Windows 11): a self-signed
  code-signing certificate `CN=Noise Filter Test Driver` in LocalMachine\My,
  trusted in Root and TrustedPublisher; `bcdedit /set testsigning on`. The package (`.sys` and catalog) signs and
  verifies. EMS (for the EC2 serial console, the script's `-Ems`) was turned on, then reverted at the owner's request
  (2026-11-20: as few changes as possible against the baseline): `ems` deleted from `{current}`, `emsport` and
  `emsbaudrate` from `{emssettings}`. Against the TMR box's boot settings (the owner's paste), this box's differ only by
  `testsigning Yes`; `{emssettings} bootems Yes` is AWS's own, on both.
  Git Bash's PSModulePath lists PowerShell 7's modules first, which leaves Windows PowerShell 5.1 without `Cert:`: the
  scripts are started with `env -u PSModulePath powershell -File ...`.
- **Not checkable from here:** the AWS key on the box can't list or make images; the AMI the clone came
  from is the pre-spike snapshot, the owner's to confirm.

   - **An outside review's findings 1 and 2, fixed in the driver (code done, built, not yet run).** The protocol's version
     stays 1 (nothing shipped); `nf_vmic.h` has the rules, `crates/nf-vmic` mirrors them separately.
     - *Format conflicts show at open time.* The ring is a separate attachment from the loopback, so a capture stream in
       24-in-32 could take the reader slot and get zeros (the mismatch branch). Now, while a ring is attached, creating a
       capture stream in any format but 48 kHz float32 stereo fails with STATUS_NOT_SUPPORTED (`RefusedCaptureOpens`), and
       an ATTACH while such a stream is open fails with STATUS_NOT_SUPPORTED, ERROR_NOT_SUPPORTED 50 (`FormatRejects`).
       Both decide under the app ring's lock, which the capture open holds around the loopback's own check and record
       (`CaptureStreamOpen`), so a non-float open and an ATTACH can't both get through. The app ring counts the other-format
       capture streams of every device itself; the loopback's records stay in its `CaptureOpen` slots. The zero-fill stays
       as the fallback. Shared-mode streams run at the device format, so this meets exclusive-mode clients only.
     - *Every running capture stream hears the ring.* Only the first capture stream to run read the ring; any other got
       silence. Whether a second one runs is not established: the capture pin lists formats only for RAW (CaptureCircuit.cpp,
       and PacketSize.cpp says every stream is RAW today), so a DEFAULT or communications client may share the RAW device
       stream, and a 3.33 ms helper beside a 10 ms client in one mode shares one too. Two of the driver's devices would make
       two (their microphones share the one app ring), and so might a pin that lists a mode besides RAW. Now the reader also
       writes what it delivers (its underrun silence included) into a 256 KiB non-paged copy at its frames on the QPC time
       line, and every other stream in the ring's format reads that copy the reader's packet plus 1 ms and a frame behind its
       own place (`SecondaryFramesCopied`, `SecondaryUnderrunFrames` in NF_VMIC_STATS; `NotReaderPackets` still counts their
       passes). The app's protocol is unchanged: one ReadFrame, paced by the reader. A handoff (the reader pauses, another
       stream takes the slot) can skip or repeat up to that lag once in the others and leave a short gap of silence.
     - *Gaps count as underruns* (a review of the fix above; built, not run). A jump in the reader's time line (a glitch
       adjustment, or a handoff seen by a third stream) leaves silence in the copy, which the other streams heard but
       `SecondaryFramesCopied` counted as the ring's audio. The copy now records its latest 16 gaps (AppRing.h), and a read
       counts their overlap in `SecondaryUnderrunFrames`, so `verify`'s check (silence inside the signal at most
       `UnderrunFrames` + `SecondaryUnderrunFrames` + a packet) holds on another stream's recording when the reader glitches.
   - **Live checks for those two** (the lead's, on the box):

## Format validation

The shipping candidate for both the render and capture endpoints is 48 kHz stereo, IEEE float32 preferred, with
signed PCM carrying 24 valid bits in a 32-bit container as the required integer fallback. Both use eight bytes per
stereo frame. ACX uses the first format added to a list without a default as that list's default. The Server A/B
also verified that Windows stored float on both endpoints and audio flowed. [ACX format list behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/acxdataformat/nf-acxdataformat-acxdataformatlistadddataformat)

- [ ] Repeat the four format-list installs from check 3 on physical Windows 11 24H2 or later. Record OS build and ACX version.
  After a bounded wait for enumeration, record parent PnP status, enabled `Speaker0` and `Microphone0` interfaces,
  and active MMDevice render and capture IDs belonging to that install. Exclude stale endpoint entries. For each
  active endpoint record `PKEY_AudioEngine_DeviceFormat` (`Get-EndpointFormat.ps1 -Match AudioCodec`), including
  subtype, rate, channels, container bits and valid bits. The dual-format candidate should activate both endpoints
  with float stored on each. Record the PCM-first default as well. Float-only is a diagnostic control.
- [x] The app's offline 24-in-32 packing regression is fixed in `d120531`. Positive full scale encodes as `0x7FFFFF00`,
  output padding is zero and input padding is ignored. [Windows PCM layout](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ksmedia/ns-ksmedia-waveformatextensible)

  Log the formats actually opened. Send a known stereo pattern with different signed values per channel. At unity
